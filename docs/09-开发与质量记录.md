## 二、关键机制与设计约束（改代码前必读）

### 1. request_id / cmd_id 是端到端闭环的关联键
云端 request_id（36 字符 UUID / 演示 40 字符）→ 网关作为下行 `cmd_id` → 设备回 ack 原样带回 → 网关按完整字符串匹配 pending 表 → 回 IOTA_CommandResponse。
**约束**：任何一端缓冲 `cmd_id` 必须 ≥64 字节（曾因设备端 32 字节静默截断导致云端命令永远超时，见缺陷 #1）。

### 2. MQTT 订阅不能覆盖自己发布的响应主题
网关订阅 `commands/#` 会命中自己发布的 `commands/response/...` → 无限自回环风暴。
**约束**：消息入口必须过滤 `/sys/commands/response/` 与 `/sys/properties/set/response/`（见缺陷 #3）。

### 3. TCP fd 生命周期与锁协议
设备表锁（`device_table` 的 g_mutex）同时保护：查找、发送、断线移除。
**约束**：
- 发送必须走 `device_table_send()`（持锁完成整个 send），不能先取 fd 再在锁外写；
- TCP 断线处理必须"先 unregister、后 close(fd)"，否则 close 后 fd 号被 accept 复用会错发命令（见缺陷 #8）。

### 4. 离线判定与上报周期挂钩
协议允许上报周期最大 600s，离线超时不能固定 60s。
**约束**：离线超时 = `max(60s, 设备上报周期×3 + 30s)`，周期来自 register 帧的 interval 字段。

### 5. 命令/属性响应必须走各自通道
- 命令下发（commands/#）→ 回 `commands/response/request_id={rid}`
- 属性设置（properties/set/#）→ 回 `properties/set/response/request_id={rid}`
**约束**：`forward_command` 只负责转发并返回状态码（0/-1 离线/-2 发送失败），由调用方决定响应通道与结果码；离线/失败不得谎报 success（见缺陷 #6）。

### 6. pending 命令表必须有超时清理
**约束**：`pending_expire()` 每上报周期执行，30s 未回执向云端回 `result_code=1`（"ack timeout"）并释放，避免内存增长与云端永久挂起。

### 7. query 是下行帧，全链路必须一致
`query` 由云端命令触发（`command_name="query"`）→ 网关发 `{type:"query"}` 帧（不是 cmd 帧）→ 设备回 data+ack。
**约束**：web 命令白名单、node-gateway 下行分发、C 网关 `protocol_build_query`、设备端处理四端对齐（曾缺失导致云端 query 变"未知命令"，见缺陷 #10）。

### 8. 模拟数据必须均值回归
温度随机游走需加向基准的弱回归项（如 `+ (base - t) * 0.03`/步），否则长时间运行漂移出告警区、大屏全红（见缺陷 #11）。
**约束**：`tools/simulate_devices.js`、`device/ui/ui_main.c`、`device/sensor.c` 三处模拟逻辑保持一致。

## 五、已知边界与教学提示

- 华为 SDK 的 `libHWMQTT.so` 为 x86-64，C 网关只能在 x86-64 Ubuntu 编译运行（板子跑不了）；本地明文演示用 node-gateway。
- `web/data/history.json` 持久化上一轮数据：重启后旧节点仍显示历史值，属预期；正式演示用 `start-all.bat` 起满 16 库即整体刷新。
- 模拟器尖峰间隔 60~120 步（演示告警可用屏幕"模拟故障"按钮或调阈值触发，更快更可控）。
- 教学建议：协议契约（docs/02、03）是四方共同遵守的"接口"，改协议先改文档；每条约束都对应一个真实踩过的坑（见第三节）。
